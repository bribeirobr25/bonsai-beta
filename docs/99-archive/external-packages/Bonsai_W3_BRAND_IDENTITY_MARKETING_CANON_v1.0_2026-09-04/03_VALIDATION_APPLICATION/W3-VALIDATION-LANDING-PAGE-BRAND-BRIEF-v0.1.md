# Bonsai · W3 · Validation Landing Page · Brand & Messaging Brief v0.1

**Date:** 4 September 2026  
**Status:** `AUTHORIZED VALIDATION APPLICATION · NOT FINAL POSITIONING`  
**Surface context provided by founder:** web app, mobile-first, desktop/tablet friendly.

## 1. Purpose

Create a landing page concrete enough for someone to understand the contemplated web-app experience and react to its value proposition.

The page is a **validation instrument**. It should help test:

- whether the immediate record/progress job is relevant;
- whether Progress makes the proposition clearer/more motivating;
- whether Memory adds value beyond organization;
- whether Continuity adds meaning or becomes abstract;
- whether the proposition feels different enough from Photos/Excel/notes to deserve attention;
- whether beginner-safe language improves comprehension without implying horticultural authority.

## 2. What this page is not

It is not:

- final Brand positioning;
- final visual identity;
- product roadmap;
- final MVP specification;
- proof P1/P2/P3 is selected;
- campaign strategy;
- permission to market unvalidated future mechanisms as existing features.

## 3. Message architecture

### Layer 1 · Hero: Progress / Keep Track

The hero should stay close to the best-supported language and immediate value.

Recommended territory:

> **keep track of your trees + see progress over time**

Do not lead the hero with `Continuity`, `Legacy`, `Provenance`, `AI`, `Expert Care` or `Community`.

### Layer 2 · Memory

Explain why records matter beyond administrative tracking:

- look back at what happened;
- connect photos and important moments to a tree;
- remember changes/interventions;
- make progress legible.

`Memory` is the strategic meaning; consumer copy should generally remain concrete.

### Layer 3 · Collection / retrieval

Particularly relevant to expanding hobbyists:

- multiple trees;
- remembering what happened to which tree;
- finding previous photos/events without reconstructing the history from scattered tools.

Do not claim a dedicated app is already superior. The landing page is partly there to test whether people perceive that advantage.

### Layer 4 · Continuity / trust

Lower on the page, explore the deeper meaning carefully:

> keeping a tree's history coherent over time

Do not use permanence guarantees.

If export/user-control is represented, it must be presented as an actual concept/commitment under test, not a vague trust badge.

### Layer 5 · Psychological Safety

Especially for beginner-oriented sections:

> start simple; you do not need to already be an expert to begin documenting progress.

Do not imply the platform guarantees correct care.

## 4. Suggested landing-page section order

1. **Hero** — keep track + progress.
2. **Progress proof/visual** — show one tree changing over time.
3. **What stays together** — photos/events/context around one tree.
4. **Why it becomes useful** — look back / remember / retrieve.
5. **As your collection grows** — collection-level memory pressure, without forcing migration claims.
6. **Continuity/trust** — deeper meaning and user-control principles, only as concrete as the represented product can support.
7. **Beginner reassurance** — learning is legitimate; no expert-performance requirement.
8. **Primary CTA / validation action** — defined by MVP Validation Strategy, not by Brand alone.

Comparable Journey should not be a core section unless explicitly shown as a future concept/hypothesis with clear labeling.

## 5. Hero-message hypotheses worth testing

These are test candidates, not final copy.

### H1 · Track + Progress

> Keep track of your bonsai and see how each tree changes over time.

Closest to the strongest observed language.

### H2 · Progress first

> See your bonsai's progress, one tree at a time.

Tests whether visible change is a stronger entry than recordkeeping.

### H3 · Memory

> Remember what happened with each tree.

Tests the W3 bridge territory.

### H4 · History / Continuity

> Keep each tree's history coherent over time.

Tests deeper meaning. Should not be assumed to outperform H1/H2.

Do not test these as preference-only slogans. The eventual validation design should connect messages to meaningful behavior where possible.

## 6. Claims permitted on the page

Only where the represented concept actually supports them:

- keep track;
- see progress;
- photos over time;
- look back;
- remember what happened;
- organize/see multiple trees, cautiously;
- access on phone/tablet/desktop if the prototype actually does so;
- user-control/export only if represented truthfully.

## 7. Claims prohibited on the page

- Never kill another bonsai.
- Know exactly what your tree needs.
- Expert care.
- AI-powered authority.
- Verified tree history.
- Learn from thousands of similar trees.
- Permanent/forever history.
- The bonsai community.
- Everything you need for bonsai.

## 8. Comparable Journey

Current status:

> `MIXED · DENSITY RISK HIGH`

The landing page must not imply that the platform can already surface robust comparable journeys at realistic `species × climate × stage/state × intervention` density.

If included in a concept variant, label it as future/conceptual and keep the output descriptive rather than prescriptive.

## 9. Visual-expression principles for this validation page

These are **not** final Visual Identity choices.

The page should feel:

- calm, not urgent;
- contemporary, not nostalgic or rustic;
- credible, not expert-theatrical;
- observational, not diagnostic;
- humane and beginner-safe, not childish;
- centered on real trees, time and visible change;
- lower in interface spectacle than in useful progression evidence.

Prefer visual proof of progression/time over generic “nature” decoration or generic AI imagery.

Avoid prestige signaling around expensive trees, awards or pedigree.

## 10. Responsive / device principle

The founder has specified a **mobile-first web app with desktop/tablet friendliness** as the presentation context.

Brand implication:

- phone = natural capture/quick look-back context;
- larger screens = useful for reviewing progression/history/collection context;
- responsive availability is supporting proof, not the Brand proposition.

Avoid leading with implementation language such as `responsive`, `PWA`, `cross-platform` unless validation specifically tests technical access expectations.

## 11. CTA principle

Brand does not choose the CTA in isolation.

The CTA must reflect the validation question selected by MVP Validation Strategy, for example:

- request access;
- join pilot;
- start a sample tree record;
- try the concept;
- compare with current workflow.

Do not default to `Buy now` or subscription language before economics/payment architecture is selected.

## 12. Interpretation rules

A strong landing-page result on Progress:

- supports message relevance;
- does not validate Memory/Continuity;
- does not prove retention;
- does not prove payment;
- does not prove dedicated-workflow superiority.

A strong result on Continuity:

- supports meaning/trust relevance;
- does not prove the operating model can truthfully fund the promise.

A weak landing-page result should not be “fixed” by escalating into more poetic language without behavioral evidence.
